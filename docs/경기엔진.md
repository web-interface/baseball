## 1. 한눈에 보기

1. **엔진은 하나다.** 내 경기·다른 구단 경기·비동기 대전·가상 과거 시즌·보정 시뮬 모두 같은 `simulateGame()` 으로 공 하나씩 던진다. 다른 구단 경기는 기록만 끈다(평균 약 0.7~0.9ms). FM 의 '빠른 계산' 엔진을 따로 만들지 않으므로 내 팀과 AI 팀의 통계가 어긋날 수 없다.
2. **카드는 엔진 데이터의 요약이다.** 선수의 '진짜 값' = 능력치 45개 + 포지션 숙련 10 + 구종(2~5개, 위력·커맨드·구사율) + 숨은 13 + 날씨 특성 6 + 특성·폼. 카드 앞면 6개와 OVR 은 이 데이터에서 계산한 묶음 값이고, 카드 레벨·강화·팀컬러·케미·폭발은 '능력치 점수'로 깊은 능력치에 더해져 엔진에 들어간다.
3. **공 하나의 흐름**: 견제·도루 출발 → 구종 선택(카운트·약점·기억·포수 리드·비) → 의도(가운데/가장자리/유인) → 실제 위치(제구·커맨드·피로·비·더위) → 노림수·지각(착시·터널링·디셉션·햇빛·안개) → 스윙 → 판정(심판 성향+프레이밍 또는 ABS) → 접촉 → 파울/인플레이 → 충돌 오프셋 타구(타구 속도·발사각·방향) → 비행표 + 공기 밀도·바람 → 담장 → 수비 '시간 경주'(반응·가속·경로·다이빙) → 송구·중계·주루 '시간 경주' → 기록.
4. **물리로 푸는 곳과 통계로 푸는 곳을 나눴다.** 비거리·바람·담장·수비 도달·송구·주루·도루·병살·땅볼 구름은 거리와 시간, 스윙·접촉·판정은 실측 카운트표에 맞춘 로지스틱. 그래서 날씨·구장·능력치가 '전체 ±10%'가 아니라 **메커니즘으로** 들어간다(갑천 볼파크 우측 7m 벽은 실제로 공을 막는다).
5. **결정성**: 시드 = HMAC-SHA256(서버 비밀, 경기 식별자) → sfc32. 투구·타구·판단마다 '키로 갈라 쓰는 서브스트림 + 고정 슬롯 16개'라서 같은 입력 = 같은 결과, 유저가 개입해도 다른 공의 난수가 밀리지 않는다. 같은 경기를 다시 요청해도 결과가 바뀌지 않는다(실측 200/200 해시 일치). **같은 프로세스가 앞서 다른 경기(연장 15회 제한·더블헤더 9회 제한)를 돌렸어도 같다**(18 심사: 전에는 WE 메모가 maxInn 을 키에 넣지 않아 15회 제한 경기 뒤 같은 경기 200개 중 7개가 달라졌다 — 서버 격리 공간 재사용·다시 보기 해시 검사에서 깨질 수 있던 문제). 선수 배열 순서도 결과에 영향이 없다(엔진이 id 순으로 정렬).
6. **보정 결과(2만 경기, 17 현실성 심사 반영)**: 삼진 .198(목표 .195) · 볼넷 .096(.093) · 홈런/타석 .0236(.0225) · 타율 .259(.265) · 출루 .339(.342) · 장타 .394(.397) · BABIP .309(.313) · 팀 득점 4.72(4.90±.35) · 홈 승률 .517(.518) · 도루 성공 .750(.745) — 명시 허용오차 228항목 중 183 통과, 시즌 20번 돌린 리그 1위 기록(타율 .350 · 홈런 40.5 · 세이브 33.6)도 KBO 범위. 경기 흐름(끝내기·미완료 타석·작전·투수 운용·주루)의 현실성 심사와 고친 내용은 `fd/out/17_현실성심사.md`.
7. **조합 보너스는 선형(기획서 결정)으로 엔진에 들어간다 — 18 심사에서 코드 반영(`bonus.mode = 'linear'`).** 압축하면 화면 게이지 서열이 경기에서 뒤집히고 폭발 순간(+15 → +25)이 승률 .585 로 거의 안 보였다(선형 .81). 실측: '노멀 풀덱(평균 팀 + 조합 29)' vs '엘리트 잡덱(OVR +20 팀 + 조합 2)' = **.727**(게이지 89 > 87 과 같은 방향). 대신 경기마다 '리그 수준 기준점 R'(`GameInput.levelRef`, 18 심사에서 코드 반영)을 빼서 엔진이 늘 보정된 범위에서 돌게 한다(3.4절) — R 없이 풀덱끼리(+37 대 +37)면 타율 .326·삼진 9.6%·홈런/타석 .077 의 '홈런 더비', R=37 이면 타율 .266·삼진 20.0%·홈런/타석 .026 으로 정상.
8. **체감**: 전원 능력치 +5 → 승률 .619, +10 → .735, +20 → .918(18 심사 뒤 재측정). 같은 구단 24명에서 25명째를 채우는 순간(폭발) 전원 약 +10 → 직전의 나보다 약 .77(R 적용)~.81. 매칭(팀 종합 ±8 ≈ 능력치 +8 → .71)·난이도 6단계가 한 경기 승률을 .30~.70 안에 묶는다.
9. **날씨는 경기 시계로 흐른다**(10분 칸 54개, 시작 −3시간 ~ +6시간). 기온 1℃ ↑ → 홈런 +1.6%(목표 +1.8%), 외야로 부는 바람 4.5m/s(구장 노출 0.4) → 홈런 +35%·안으로 −41%, 비 → 실책 +20%·폭투 +60%·볼넷 +21%, 4mm/h 이상 중단·30분 대기·90분 넘으면 콜드/노게임. 선수마다 숨은 날씨 특성 6종이 그 판정의 날씨 패널티에만 곱해진다.
10. **이벤트 109개·상호작용 350개**는 확률을 조금(심리층 ±12%·물리층 ±35%·최종 ×0.6~×1.6), 이야기를 크게 바꾼다. 켬/끔 비교에서 리그 득점 차 −0.34%, 홈 승률 차 +0.2%p.
11. **성능**: 평균 0.69~0.86ms/경기(기록 끔 — 측정 때 같은 컴퓨터의 다른 작업 부하에 따라)·0.80ms(기록 켬), p99 1.5~2.9ms, 투구 310개. 극단 시험(전원 99 vs 1·20회 제한·명령 폭탄) 최악 p99 4.5ms·최대 5.4ms, 한 경기 1,000구 안전 상한(콜드)으로 명령 수에 비례해 늘지 않는다(18 심사). 요청 하나(10ms CPU)에 내 경기 1 + 다른 경기 4 까지(14절 과제 17 의 Workers 실측으로 확인할 것). 기록(2D 중계 테이프) 평균 17.1KB, gzip 6.5KB.
12. **Claude(claude-sonnet-5-5)는 글만 쓴다.** 결과가 저장된 뒤, 유저가 리포트를 열 때 별도 요청으로 하이라이트·인터뷰만. 하루 상한 = (180 − 누적) ÷ 남은 운영일 ≈ $0.49, 누적 $180 에서 영구 차단 → $200 을 넘을 수 없다.

### 2.3 의존 방향

```
types ← params ← rng
player(params, rng) ← state ← we
pitch(player, state, we, weather) ← batted(data/flight) ← fielding ← running(log)
tactics(pitch, we, fatigue, events, log) ← events(data/events, log) ← injury(data/injuries)
game(모두) ← index        season(fatigue, injury, weather) · generate(15 스키마는 호출 쪽이 넘김)
```
- 엔진 번들은 `15_player_schema.json`(270KB)을 싣지 않는다. 생성기는 스키마를 인자로 받는다(서버·도구가 읽어서 넘김).
- 모든 무작위는 `rng.ts` 만 쓴다. `Math.random`·`Date.now()`·`performance.now()` 를 결과 계산에 쓰지 않는다.

### 3.3 카드 6칸 → 깊은 능력치 대응표 (엔진 보너스 벡터)

보너스는 두 형태다.

- **A형 '전 능력' 보너스**(강화·팀컬러 메인·그해 덱·유닛·케미·지휘·품격·폭발·각성·MVP 각인): 성향 4개를 뺀 능력치 41개 + 구종 위력·커맨드 전부에 같은 점수. 상세 화면(FM 45칸)도 41칸이 함께 오른 실효 값을 보여 준다.
- **B형 '묶음' 보너스**(레벨 성장·플레이스타일·각인·특수 팀컬러·장비·GG/TH 각인): 그 카드 칸을 이루는 깊은 능력치에만 같은 점수 → 카드 칸이 정확히 그만큼 오른다(묶음 가중치 합 = 1).

### 3.4 선형 합산과 리그 수준 기준점 R — '능력치 폭발'의 엔진 쪽 규칙 (결정)

**결정: 보너스는 압축하지 않는다(기획서 3.6과 같음). 15·11 초안의 `20(1−e^(−B/20))` 압축은 폐기한다.**

| 안 | 노멀 풀덱(평균 팀 + 조합 29) vs 엘리트 잡덱(OVR +20 팀 + 조합 2) | 화면 게이지 | 판정 |
|---|---|---|---|
| 압축(k=20) | 엘리트 잡덱 우세(60+15.3 ≈ 75 대 85+1.9 ≈ 87 — 기획서 3.6 계산) | 89 대 87(풀덱 우세) | ✗ 화면과 경기가 거꾸로 |
| **선형** | **풀덱 .703** (실측 1,500경기, zGain .25, `chief_sens.ts`) | 89 대 87 | ○ 같은 방향 |

- 이유 ① 사용자 원문 "풋볼데이인데 … 다맞추면 능력치 폭발" — 원작 「같은 팀 무명 선수들만 모아놓은 게 훨씬 쎄다」가 경기에서도 성립해야 한다. ② "엔진 데이터 최우선"은 화면 숫자가 엔진 효과의 정직한 요약이라는 뜻이다. 압축하면 카드 숫자가 엔진과 다르게 말한다. ③ 보너스마다 상한이 있어(카드 칸·슬롯 130, 팀 쪽 합 +37) 야구9단식 무한 인플레는 생기지 않는다.

**R(리그 수준 기준점)**: 덱이 강해질수록 양 팀 모두 능력치가 +30 가까이 올라가면, 엔진이 보정된 범위(1군 주전 평균 = 진짜 값 60 근처)를 벗어나 삼진·실책 같은 리그 통계가 틀어진다. 그래서 **경기마다 양 팀이 공통으로 가진 수준만큼을 모든 선수에게서 똑같이 뺀다.** 차이는 그대로 남고, 엔진은 늘 보정된 범위에서 돈다(같은 리그 안의 2군 경기도 야구처럼 보이는 것과 같은 원리).

```
T(팀)  = 0.5 × 타순 9명 슬롯 OVR 평균 + 0.3 × 선발 투수 슬롯 OVR + 0.2 × 불펜 상위 4명 슬롯 OVR 평균
R      = clamp( (T_home + T_away)/2 − C_ref , −20, 60 )
C_ref  = 61.0   ← 보정 리그(생성기 1군 주전)의 같은 T 값(측정해 확정, 14절 과제 3)
엔진 입력 값 = a_i + B_i − R       (성향 4개 제외, 구종 위력·커맨드에도 같은 R)
```
- R 은 서버가 계산해 `GameInput.levelRef` 로 넘긴다(**18 심사에서 엔진 쪽 반영**: 성향 4개 뺀 능력치 41개와 구종 위력·커맨드에서 소프트캡 전에 똑같이 뺀다. 서버의 T·C_ref 계산은 14절 과제 3). 양 팀 같은 값이라 러버밴딩이 아니다(약팀을 몰래 돕지 않는다 — 차이는 보존). 실측(1,200경기): 폭발 순간 +25 vs +15 는 R 없이 .809 · R=20 .767, 풀세트 +25 vs 잡덱 +2 는 .970 · R=13.5 .946 — R 은 리그 통계를 정상으로 돌리고 실력 차의 승률은 거의 그대로 둔다.
- 소프트캡(90)은 R 을 뺀 뒤에 건다. 그래서 '리그에서 압도적인 한 선수'만 캡에 닿는다.
- 시즌 기록은 리그 상대값이 된다(같은 선수가 강한 리그에서 덜 친다 — 실제 야구와 같다).

### 3.5 포지션 적성 — 엔진 숙련 하나로 통일 (결정)

- 진짜 기준은 선수의 포지션 숙련 `pos[10]`(1~20, FM 포지션 원). 수비 배율 m(prof): 1 → 0.50, 5 → 0.68, 7 → 0.76, 10 → 0.84, 12 → 0.88, 15 → 0.94, 18 → 0.98, 20 → 1.00(사이는 직선 보간).
- 카드 화면의 적성 기호는 이 숙련에서 정한다: **◎ 18~20 · ○ 15~17 · △ 10~14 · × 5~9 · ⚠ 1~4**. 기획서 3.3 배율(1.00 / 0.95 / 0.85 / 0.70 / 0.50)은 각 구간의 대표값과 같다 → 게이지 계산은 기획서 배율 대신 `m(prof)` 를 그대로 쓴다(화면 = 엔진).
- 엔진은 배율을 수비 묶음(range·firstStep·hands·turnDP)과 **armAcc** 에만 곱하고 armStr 은 곱하지 않는다(어깨 힘은 자리를 바꿔도 같다). 그래서 카드 어깨 칸의 적성 배율 = **0.7 + 0.3·m** 으로 기획서를 고친다(ARM = 0.7·armStr + 0.3·armAcc 이므로 정확히 같아진다).
- 기획서 규칙 '포수 적성은 포수 카드만'·'1루는 누구나 △ 이상'은 생성기의 숙련 기본값(포지션 유사도 표)에서 그대로 성립한다(비포수 C 숙련 1~4, 1루 10 이상).
- 낯선 포지션(숙련 10 미만) 출장: 그 경기 실책 ×1.30·범위 −5%(물리층), 사기 −2(이벤트 `form_out_of_position`).

- **타석 접근법(approach)의 대가·맞대응**(18 심사): 장타(power) = 배트 +1.5km/h·노림수 ×1.3·스윙 +0.10 대신 **접촉 로짓 −0.30**, 배터리는 존 밖으로 조금(의도 −0.10·gq) · 맞히기(contact) = 배트 −1km/h·노림수 ×0.6 대신 **접촉 +0.30** · 기다려(patient) = 스윙 −0.25 인데 **배터리가 존 안으로 밀어붙임**(의도 +0.25·gq) · 진루타·희생타(AI 상황용 5·6) 접촉 +0.15. 실측(같은 시드 짝, 1,500경기): 모든 타석 같은 접근법의 승률 차가 전 power +4.6·patient +3.8·contact −6.7%p → 후 +2.6·−0.5·−2.3%p(적극 −2.0) — 한 가지가 늘 정답이 아니다.

### 5.5 유저 개입 (`Command`)

- 명령에는 `at`(적용할 투구 번호)이 붙는다. 서버는 받은 순간 **아직 공개되지 않은 다음 투구 번호**를 찍어 저장하고(10.4 라이브), 엔진은 그 투구를 던지기 직전에 적용한다 → "다음 투구 전에 반영", 이미 본 공은 못 바꾼다. **`at` 은 서버가 찍는다 — 유저가 보낸 `at` 을 그대로 쓰면 이미 본 공 앞에 명령을 끼워 결과를 다시 고를 수 있다.** 명령의 `team` 도 서버가 인증으로 정한다.
- 지금 엔진이 처리하는 명령: `steal`(2·3루) · `hitRun` · `bunt`(sac·drag·squeeze) · `take` · `swingAway` · `approach` · `pitchout` · `ibb`(18 심사: 아무 카운트에서나 자동 고의4구) · `infield`(normal·dp·in·cornersIn, 고정) · `outfield`(normal·deep·shallow, 고정) · `pitcher`(교체) · `pinchHit` · `pinchRun` · `auto`(켜면 AI 코치가 대신, 끄면 투수 교체·대타·고의4구도 묻기만).
- **엔진 쪽 검증(18 재미·악용 심사)** — 서버가 걸러도 엔진이 한 번 더 막는다:

| 규칙 | 막는 악용(실측, 고치기 전) |
|---|---|
| 유저 팀(`isUser`) 명령만 적용, 상대 팀 이름의 명령은 버림 | 상대에게 매 투구 희생번트 → 유저 승률 약 .45 → .94 |
| `pitcher`: 불펜 명단에 있고 avail ≥ 1(0 = 사흘 연속·어제 30구↑ 등 등판 불가), 아직 안 던졌고, 지금 투수가 아니고, 수비에 서 있지 않고, 구종이 있는 선수만 | ① 지금 투수를 다시 '교체' → 피로 0으로 되돌림(수동 모드 선발 평균 154구·8.8이닝, 다음 날 피로엔 뒤 등판분만) ② 등판 불가 투수 투입(혹사 비용 없이 +3.1%p) ③ 야수·구종 없는 선수 등판 → 투구 계산이 멈출 수 있음 |
| `pitchout`: 뛸 수 있는 주자(1루 주자·2루 빔 또는 2루 주자·3루 빔)가 있을 때만 | 매 투구 피치아웃 = 끝없는 볼넷(한 경기 3,400구·상대 212점·CPU 7.7ms) |
| 명령은 보낸 순서로 앞 1,000개(= 투구 상한)만, 유한한 `at` 만, 번호 순 · 한 경기 1,000구가 되면 그 자리 콜드(점수 그대로, 같으면 무승부) | NaN 번호 하나가 뒤 명령을 전부 막음 · 명령 폭탄으로 CPU 증가·끝나지 않는 경기로 결과 무효화 시도. 퍼징(무작위 명령 최대 3,000개·없는 선수·NaN·범위 밖 전술 1,500경기): 예외 0·비결정 0·CPU p99 5.0ms |
| 대타·대주자·투수 교체는 **그 타석부터** 적용(타석 문맥·장부를 새 선수로 다시 잡음), 테이프에 교체 기록 | 고치기 전에는 대타를 내도 빠진 타자가 그 타석을 치고 새 투수를 올려도 앞 투수가 그 타석을 던졌다(시험 120경기 중 0번 적용 → 고친 뒤 대타 119/120, 투수 106/120 — 나머지는 이미 쓴 투수라 거부) |

- AI 난수 키가 (타석, 판단 종류)라 유저가 한 판단을 가져가도 다른 판단의 난수는 그대로다. 실측: 투구 120번에 명령 → 그 전 테이프 접두 동일, 그 뒤 결과 변경.
- 아직 안 되는 것(타입만 있음): `pickoff`·`visit`·`review`·`defSub`.

## 10. 리그 운영 — 지연 계산 · 시드 · 저장 · 무료 한도

### 10.1 시드

```
경기:   seed = HMAC-SHA256(SERVER_SECRET, `game|{리그}|{시즌}|{경기일}|{경기번호}|{홈}|{원정}|{engineVer}`)[0..16] → 4 × uint32
날씨:   seed = HMAC(SECRET, `wx|{리그}|{시즌}|{도시}|{날짜}`), 시즌 체제 `wx|{리그}|{시즌}|regime`   (경기 시드와 분리 → 예보를 보여 줘도 경기는 계산 불가)
대전:   seed = HMAC(SECRET, `pvp|{대전 id}|{engineVer}`)   (대전 id 는 첫 요청 때 서버가 만들고 request_id 고유 키로 묶음)
도구:   seedFromString(문자열) — 서버 비밀 없음, 보정·시험 전용
```
- 기록에는 시드를 남기지 않는다(`seedTag` = 시드 일부 해시 8자). 엔진 버전을 시드 문자열에 넣고, 진행 중인 경기는 시작할 때의 버전으로 끝까지 돈다(배포 때 직전 버전 1개를 번들에 유지).
- **시드 악용 점검(18 심사, `fd/engine-proto/fx/t7_seed.ts`·`t7b_memo.ts`)**: 같은 입력 200/200 같음 · 앞서 9회 제한·15회 제한 경기를 돌린 프로세스에서도 200/200 같음(고치기 전 15회 제한 뒤 193/200) · 의미 없는 변화(경기 id 글자·기록 켬·선수 배열 순서·불펜 순서·AI 팀에 보낸 명령·라이브 지평)로 결과가 바뀌지 않음 · 라이브 지평까지의 테이프 = 전체 계산의 앞부분(50/50). 벤치 순서(대타 우선순위)·타순을 바꾸면 결과가 달라지는 것은 정상 입력이다 — 그래서 **서버는 경기 입력(라인업·벤치·전술)을 결과 계산 전에 잠그고, 공개된 경기의 입력 변경을 받지 않는다.** 시드만 바꿔도 원정 승리 경기의 약 48% 가 뒤집히므로(야구의 운) 시드에 유저가 고를 수 있는 값을 절대 넣지 않는다.

### 10.2 지연 계산(따라잡기)

- 경기일 k 의 시각 T_k 는 시즌 시작 때 고정(커리어: 유저가 '다음 경기일' 또는 '시즌 자동 진행'을 누를 때 진행). 요청이 오면 아직 계산 안 된 경기일을 **번호 순서대로** 계산한다(어제의 피로·부상·컨디션이 오늘 입력이라 순서가 곧 결과).
- **요청 하나의 일감** = 경기일 1일: 내 경기 1(기록 켬) + 다른 구단 경기 4(기록 끔). CPU = 0.80 + 4 × 0.70 + 입력 파싱·상태 갱신 약 1.5ms ≈ **5ms**(10ms 의 절반). Workers 는 요청 안에서 시간이 흐르지 않아 CPU 를 잴 수 없으므로 '일의 양'으로 예산을 잡는다(경기 5개 또는 투구 1,500개에서 멈춤).
- 같은 날 5경기는 서로 독립 → 경기 번호 순 계산, 상태 갱신(`afterGame`)은 5경기가 끝난 뒤 한꺼번에.
- 저장은 `INSERT … ON CONFLICT DO NOTHING`(키 = 리그·시즌·경기일) → 동시에 두 요청이 계산해도 결정적이라 같은 결과, 한 행만 남는다. **새로고침 재추첨이 원천적으로 불가능.**

### 10.3 저장(무엇을 남기나)

| 무엇 | 언제 | 크기 |
|---|---|---|
| 경기일 묶음 1행: 5경기 박스스코어(gzip) + 순위 + 선수 상태 변화(피로·팔·감각·컨디션·부상) | 경기일마다 | 약 8KB |

### 11.1 원칙

- 한 경기 = `GameRecord` 하나. 정수 배열 위주(JSON), 평균 17.1KB · 최대 24.2KB, gzip 평균 6.5KB. 웹은 이 테이프만 재생한다(재계산 금지 — 부동소수점 끝자리가 기기마다 다를 수 있어 서버 결과가 정답).
- 단위: 길이 dm(0.1m) · 투구 위치 cm · 시간 cs(0.01초) · 속도 km/h×10 또는 dm/s · 각도 0.1° · 확률 ‰.
- 좌표: 홈 (0,0), x = 1루 쪽 +, y = 중견 쪽 +(m). 베이스 1루 (19.40, 19.40) · 2루 (0, 38.80) · 3루 (−19.40, 19.40). 투구 x = 포수 시점 1루 쪽 +, z = 땅에서 높이.
- 선수는 기록 번호(0~51)로 부르고 `dict[번호] = pid`.

### 11.3 웹 재생

- 투구: `pt` 의 x·z 로 포수 시점 존 그림, 구종 색, 구속. 타구: `bb` 의 체공·꼭짓점으로 포물선(높이는 거리 비율 10지점 보간 대신 2차 곡선 근사로 충분), `fd`·`th`·`rn` 으로 야수·공·주자를 같은 시계(cs)에 맞춰 움직인다. 수비 범위 원 = 반응 뒤 `reachIn(t)`.
- 승리확률 그래프 = `wp`, 주요 장면 = `pa[WPA]` 상위, 빨리 보기(1~9회 10초) = 반 이닝 득점.

## 12. Claude 문자 중계 연결

### 12.1 언제만 부르나

| 쓰임 | 조건 | 입력 → 출력 | 1회 비용 |
|---|---|---|---|
| 경기 하이라이트(3문장) | 유저가 **리포트를 열 때** + 그 경기에 우선순위 4 이상 이벤트(끝내기·대역전·벤치 클리어링·노히트·사이클·대기록 등) | 사실 JSON 1,550토큰(시스템 1,100 캐시) → 260 | $0.0037 |
| 수훈 선수 인터뷰 | 유저가 버튼을 누를 때 | 1,600 → 330 | $0.0045 |
| 리그 소식 묶음 | 하루 1번, Batch API(50%) | 3,600 → 700 | $0.0061 |
| 그 밖의 중계 문장 | 언제나 | **코드 문장 틀**(이벤트 코드·테이프 값 → 템플릿, 시드로 문장 고름) | $0 |

- **경기 시뮬레이션 요청 안에서는 절대 부르지 않는다**(CPU 10ms·결정성 보호). 결과 저장 → 유저가 열 때 별도 요청 → 생성 글을 `ai_texts`(키 = 경기 id·종류)에 저장 → 다시 열면 재사용. 두 유저 팀 맞대결은 글 1개 공유.
- 입력은 **엔진이 확정한 사실만**: 팀·이닝·점수 전후·주인공·플레이(테이프 값)·이벤트 목록·날씨 로그·원인 표시. 출력은 JSON 스키마(문장 배열), 어떤 수치에도 다시 들어가지 않는다. 결과·확률·이벤트 발생은 AI 가 정하지 않는다.
- 호출 설정: 모델 `claude-sonnet-5-5` 하나(다른 모델로 넘기는 fallbacks 금지), `thinking: {type: "between_tools"}`, `output_config: {effort: "low"}`, `max_tokens` 600, 시스템 프롬프트 `cache_control`. `stop_reason` 이 `refusal`·`max_tokens` 이거나 글 속 숫자·이름이 입력과 다르거나 금지 목록(실명·실제 구단·비하)에 걸리면 **버리고 템플릿**(재호출 없음).

### 12.2 하루 비용

```
하루 상한 = (180 − 누적) ÷ 남은 운영 목표 일수(365)  ≈ $0.49
  배분: 경기 글 60%($0.29) · 스카우트 말 25% · 레전드 사연·시상식·축하 15%
경기 글 $0.29 → 하이라이트 약 78개, 또는 소식 1 + 하이라이트 50 + 인터뷰 20
시험 30명: 1인 하루 하이라이트 2·인터뷰 1 상한 → 수요 최대 30×(2×0.0037 + 0.0045) = $0.36 → 상한에서 잘림(우선순위: 소식 > 우선순위 5 하이라이트 > 인터뷰 > 우선순위 4)
누적: 1차 일괄(카드 소개·상징 사연) 약 $2 + 하루 상한 × 운영일 ≤ $180 (조건부 UPDATE 예약 → 동시 요청에도 초과 불가) → $200 절대 미만
```
- 지금 서버(`worker/src/index.ts`)의 비용 계산은 입력·출력 토큰만 더한다 → **캐시 쓰기·읽기 토큰을 더해야** 차단이 정확하다(기획서 16.2, 과제 13).
